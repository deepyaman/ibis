## 1. Verdict

Not mergeable as a unit yet, but for different reasons than the first review. The relational design is now right: the converter reads the qualified `sge.Select` and the planner is gone, so the first review's B1 (constructs the planner discarded), B2 (derived tables) and B3 (the rounding comparator) are fixed and verified here. My fresh 358-query battery finds no wrong result in the relational skeleton; every silent-wrong case is in the value layer, each a local fix. What blocks are: (B1) `import ibis` fails on every sqlglot release below 27.11 while `pyproject.toml` still says `>=23.4`, because `convert_ranking` registers `sge.Rank` and friends at import; the branch's `_SET_OPERATION` absorption is dead code because the module dies earlier (`_arg`, for the 28.0 `with_` rename, is live and verified at 27.29.0). (B2) On sqlglot 30.8 and later, `NOT LIKE` and `NOT ILIKE` silently become `LIKE`: TPC-H q13 and q16 return 4 and 150 rows instead of 39 and 4561 on the current sqlglot release (30.24.0). "22/22 TPC-H" is true only at the locked 28.9. (B3) Eight silent-wrong value rules that everyday SQL hits: `IS [NOT] TRUE/FALSE` on NULL, window frames written without `BETWEEN` (`ROWS 1 PRECEDING`, `RANGE UNBOUNDED PRECEDING`, `ROWS CURRENT ROW`), `FILTER (WHERE ...)` on a window losing its default frame, `OVER (w ORDER BY ...)` losing the named window's partition, `CONCAT_WS`, and decimal literals typed as float64. (B4) `COUNT(1)`, `ROW_NUMBER() OVER ()`, `DATE_ADD(d, INTERVAL 1 DAY)` die with raw Python `AttributeError`/`TypeError`. (B5) The decompile round trip changes semantics for `EXCEPT ALL`/`INTERSECT ALL` and renames every aliased `NOT`/negation. All of these are small; none needs the design revisited. Recommended path: the first review's sequencing stands (simplify fix, decompile rules, harness, converter), plus a floor decision with a CI leg at the floor and at latest sqlglot before the converter PR.

## 3. Blocking issues

**B1. `import ibis` fails below sqlglot 27.11.** `convert_ranking` (`sql.py:1080-1098`) registers `sge.RowNumber`, `sge.Rank`, `sge.DenseRank`, `sge.PercentRank`, `sge.CumeDist` at import and `_ranking_functions` indexes them; `convert_ntile` registers `sge.Ntile`. None of the last five exist before 27.11.0, and the declared floor is `>=23.4`. This is worse than the first review's B4 (`SetOperation` below 26, which the branch absorbed with `getattr`): `_SET_OPERATION` is now dead code (`SetOperation` is missing only below 26, where the module raises 1000 lines later); `_arg` still earns its keep on 27.11 through 27.29, verified at 27.29.0. The notes' Phase A claim "renames absorbed" and the B4 list of "classes registered at import since Phase A" both miss these (they list `SplitPart`, `LogicalOr`, ... `Fetch` but not the ranking classes). Options, in order of preference for this repo: raise the floor to `>=27.11` in its own `fix(deps)` commit with the reason in the body, and add a CI leg that installs the floor; or absorb version-agnostically (`for name, method in (("Rank", "rank"), ...): if (cls := getattr(sge, name, None)) is not None: _convert.register(cls)(...)`), which keeps the floor but leaves ranking functions unsupported there. Do not branch on `sqlglot.__version__` in source. Whichever way, `uv.lock` at 28.9 means CI currently tests neither end of the declared range.

**B2. `NOT LIKE` / `NOT ILIKE` silently drop the NOT on sqlglot >= 30.8.** `sge.Like`/`sge.ILike` gained a `negate` arg (parsed from `NOT LIKE`) in 30.8.0; `convert_like` and `convert_ilike` (`sql.py:996-1007`) ignore it. On 30.24.0 TPC-H q13 (`o_comment NOT LIKE '%special%requests%'` in a LEFT JOIN ON) returns 4 rows for 39, q16 (`s_comment LIKE` under `NOT IN`, plus `p_type NOT LIKE 'MEDIUM POLISHED%'`) 150 for 4561, and the everyday suite passes only because no case uses `NOT LIKE`. There is no upper bound in `pyproject.toml`, so a user with current sqlglot gets wrong rows from a function that otherwise raises for anything it cannot do. Fix: read `like.args.get("negate")` and invert (version-agnostic: the arg is simply absent on older versions). Add `NOT LIKE`/`NOT ILIKE` to `CASES` and a CI leg at the latest sqlglot so the gate catches the next such change (sqlglot has done this before: `with` -> `with_`, `SetOperation`, `Limit.limit_options`).

**B3. Silent wrong results in the value layer** (each reproduces with the branch's own comparator; row counts are from `battery2.py`):
- `x IS TRUE` / `IS FALSE` / `IS NOT TRUE` / `IS NOT FALSE`: `convert_is` (`sql.py:988-993`) returns `this == literal`, so a NULL operand gives NULL where SQL gives FALSE/TRUE. `SELECT a FROM t WHERE (a > 1) IS NOT TRUE` returns 1 row for 2; `IS NOT FALSE` 3 for 4; in a SELECT list `(a > 1) IS TRUE` yields NULL for FALSE. Fix: `IS TRUE` is `this.fill_null(False)`, `IS FALSE` is `(~this).fill_null(False)`; the surrounding `Not(...)` then falls out right.
- Window frames without `BETWEEN`: sqlglot parses `ROWS 1 PRECEDING` as `WindowSpec(start="1", start_side="PRECEDING", end=None)` (`parser.py`, `_parse_window`: `end = ... if self._match(TokenType.AND) else {}`), and `_window_bound(None)` (`sql.py:1138-1149`) reads `None` as UNBOUNDED, so the frame becomes `1 PRECEDING AND UNBOUNDED FOLLOWING`. SQL says a single bound is the start and the end is CURRENT ROW. `SUM(c) OVER (ORDER BY a ROWS 1 PRECEDING)`, `RANGE UNBOUNDED PRECEDING` and `ROWS CURRENT ROW` all return the partition-to-end sum (8.5 at row 0 for 1.5). Fix: when `spec.args.get("end") is None`, the end is `0`.
- `FILTER (WHERE ...)` on an ordered aggregate window: the default-frame rule in `convert_window` (`sql.py:1178`) tests `isinstance(window.this, sge.AggFunc)`; with a FILTER `window.this` is `sge.Filter`, so the frame is the whole partition. `SUM(c) FILTER (WHERE a > 1) OVER (ORDER BY a)` returns 6.5 at every row for the running sum. Fix: unwrap `sge.Filter` before the test (the branch already does this in `_metric_units`).
- `OVER (w ORDER BY a)` extending a named window: `convert_window` (`sql.py:1154-1160`) uses the WINDOW clause only when the inline spec is empty; with an inline ORDER BY it takes the inline spec and drops `w`'s `PARTITION BY b`. Result 8.0 for 2.5 at row 1. Fix: merge (SQL allows the inline part to add ORDER BY and a frame to the named window, not a partition).
- `CONCAT_WS(sep, ...)`: `sge.ConcatWs` subclasses `sge.Concat`, so `convert_concat` (`sql.py:1271`) treats the separator as the first operand: `'-barx'` for `'bar-x'`. Fix: register `ConcatWs` and either join with the separator or raise.
- Decimal literals: `convert_literal` (`sql.py:868-874`) makes every non-integer number a Python float, so `1.10` is float64 where DuckDB types it DECIMAL(3, 2) (sqlglot's `annotate_types` also says DOUBLE, so the type has to come from the literal's text). `SELECT CAST(1.10 AS VARCHAR)` gives `'1.1'` for `'1.10'`; `0.1 + 0.2 = 0.3` happens to agree only because the comparator admits 1e-9. Fix: `ibis.literal(decimal.Decimal(text))` for a non-integer literal written without an exponent.
- `SUBSTRING(b, a - 1, 1)`: the literal-start check (`sql.py:1405-1414`) cannot see a computed start of 0, and Ibis's negative start counts from the end: `'b'` for `''`. Low priority; a note in the docstring or a `CASE` guard.

**B4. Everyday SQL that dies with a raw Python error** (the first review's B5 asked for `UnsupportedOperationError`/`IbisInputError` everywhere; `convert` wraps only `TypeError` and `ValidationError`):
- `COUNT(1)`: `convert_count` (`sql.py:1311-1321`) calls `.count()` on `ibis.literal(1)` -> `AttributeError: 'IntegerScalar' object has no attribute 'count'`. `COUNT(1)` is as common as `COUNT(*)`; treat a constant argument as `COUNT(*)`.
- `ROW_NUMBER() OVER ()` (and any ranking function with an empty window): `Value.over` returns a `Deferred` when neither the function nor the window references a table, and `_unique_names` (`sql.py:261-271`) then fails with `TypeError: unhashable type: 'Deferred'`. Bind the window on `scope.rel` (`window.bind(scope.rel)`), or resolve the Deferred through the projection.
- `DATE_ADD(d, INTERVAL 1 DAY)`: `convert_date_add` (`sql.py:1507-1516`) assumes the second argument is a number and calls `.as_interval` on the `IntervalScalar` that `convert(sge.Interval)` returns -> `AttributeError`. This is the MySQL/Spark spelling of date arithmetic.
- `LENGTH(NULL)` -> `AttributeError: 'NullScalar' object has no attribute 'length'` (`convert_null` ignores the type `annotate_types` attached); `SUM((SELECT COUNT(*) ...))` -> `AttributeError` on the scalar subquery. Rare, but the fix for both is one line: catch `AttributeError` in `convert` (`sql.py:816-826`) and raise `_invalid(...)`.

**B5. The decompile round trip is not semantics-preserving.** Found by running `battery2.py` in roundtrip mode; none is covered by the gate:
- `EXCEPT ALL` / `INTERSECT ALL`: the `union` rule (`decompile.py:391-396`) renders `distinct=True` only when set and nothing otherwise; `Table.difference`/`intersect` default to `distinct=True`, so `t.select(t.a).difference(u.select(u.a))` rebuilds as EXCEPT. 1 row for 2, 4 for 5. Pre-existing rule, newly reachable from `parse_sql`. Render `distinct=` always (or per op default).
- Aliased `NOT`/negation: `not_` and `negate` (`decompile.py:173-203`) render `~expr`, and `alias` (`decompile.py:432`) appends `.name("x")`, giving `~((t.a > 1)).name('x')`; Python applies `.name` first, so the rebuilt column is `Not(x)`. Six of my cases change name on round trip (`NOT (a > 1) AS x`, `b IS NOT NULL AS nn`, `a NOT IN (...)`, `-(-a)`, `NOT EXISTS (...) AS ne`). `_maybe_add_parens` (`decompile.py:80`) only parenthesizes `ops.Binary`; extend it to `ops.Unary`, or have `alias` parenthesize.
- A literal-only expression folds in Python: `SELECT 0.1 + 0.2 = 0.3 AS eq` renders `((0.1 + 0.2)) == 0.3).name('eq')` -> `AttributeError: 'bool' object has no attribute 'name'`. `SELECT 1 + 1 AS two` survives only because the shared literal becomes a variable. The `literal` rule's "plain Python value when the inferred type matches" needs to keep `ibis.literal` for the left operand of an infix op.
- `WITH x AS (SELECT * FROM t WHERE a > 1) SELECT a FROM x WHERE EXISTS (SELECT 1 FROM x x2 WHERE x2.a = x.a AND x2.b <> x.b)` parses and runs, but the decompiled code raises `ValueError: too many values to unpack` in `resolve_exists_subquery` (`logical.py:330`): `subsequent_filters` (`rewrites.py:386`) merges the outer filter into `t.filter(greater, (...).any())` while the EXISTS predicate still references the CTE's Filter `f`, so `.any()` sees two candidate outers. The first review's "no `ops.Subquery` in the predicates" guard for `reorder_filter_project` is needed on `subsequent_filters` too.
- Nested EXISTS inside EXISTS still rebuilds to `TypeError: The truth value of Deferred objects is not defined` (known from the notes). `ops.IntervalFromInteger` renders as `.interval_from_integer(...)` (should be `as_interval`; `d + INTERVAL (a) DAY` parses but does not round-trip). `NULLIF` still renders `.null_if`, flagged in the first review and in the notes as assigned to the decompile PR; it is not done.

## 5. The four settled rules, probed

I tried to break each rule the notes declare off-limits and could not:
- Hoisting (`_build_from`, `_hoistable`): comma joins followed by LEFT, RIGHT and FULL links, a comma link after a RIGHT join, OR-ed and BETWEEN conditions across two members, four-member chains, self comma joins, conditions through CTE and derived members, a comma join inside an EXISTS with a correlated conjunct, and conjuncts carrying subqueries all match DuckDB. The `test_sql.py` unit tests cover the two structural claims (keys become the link's predicates; nothing hoists before a RIGHT join).
- Scope: correlated references through a join member after a filter (the dropped-key case), through two derived levels, into HAVING, ORDER BY and a CTE referenced from another CTE's subquery, same-alias shadowing inside a subquery, and references from two outer levels all resolve correctly.
- Aggregate memo: a metric reused inside CASE, a window PARTITION BY, `SUM(SUM(c)) OVER`, `RANK() OVER (ORDER BY COUNT(DISTINCT b))`, `COUNT(*)` in both an outer aggregate and a correlated subquery, group expressions in HAVING/ORDER BY, qualified group columns in HAVING, and aggregates over join members all give the right rows. The documented edge (a window whose argument equals a metric) raises as the notes say.
- Anchor: correlated scalar subqueries over Filter, Sort+Limit, Distinct, Project, Union, Join, Aggregate and a filtered CTE, including two correlated subqueries on one outer and correlation in both WHERE and SELECT, all compile with a stable alias and match.
