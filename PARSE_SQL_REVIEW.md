# Review: `feat/parse-sql-subquery-prototype` (6 commits on 799a2a959)

Independent maintainer-style review by a fresh Fable 5.1 session (xhigh effort). Verbatim.

## 1. Verdict

Not mergeable as-is, and I would not frame it as "fix the list and merge" either: I would ask for a different approach to the *relational skeleton* while keeping most of what the branch built. The test harness (execute-and-compare against DuckDB for TPC-H, TPC-DS and everyday SQL), the scalar/function translation layer, the decompiler rendering rules and the `simplify` window fix are real, verifiable progress (my own 184-query battery goes from 50 ok / 10 silently wrong / 124 errors on the base commit to 143 / 5 / 36 on the branch). But the branch's central architectural claim, "the planner is sound; every silent-wrong case was a gap in the Ibis conversion code", does not survive testing. The planner silently discards information that is not needed for *execution* (DISTINCT ON, QUALIFY, OFFSET before sqlglot 30.18, the projections of a derived table once `merge_subqueries` is dropped, which side of a set operation is left), and about 400 of the ~900 new lines in `ibis/expr/sql.py` exist to reverse-engineer planner artifacts (`_a_N`, `_g_N`, `_h`, `_o_N`, `_w_N`, set-valued dependency order, join keys that are not join keys, derived-table aliases that vanish). The rule-set change that makes correlated subqueries work (dropping `merge_subqueries`) regresses the most ordinary derived-table shape there is (`SELECT s.z FROM (SELECT a + c AS z FROM t) s` fails on the branch and worked on main), and tobymao has said in so many words that the planner "is used to facilitate execution" and reverted a fidelity fix as "not necessary". The branch is in fact already half off the planner: CTEs and set operations are converted from the optimized AST in `convert_select`/`convert_set_operation` because the planner loses them. Finishing that move (convert the qualified, optimized `sge.Select` directly; keep the optimizer, drop `sqlglot.planner`) would remove most of the special cases, fix the derived-table regression class, and make unsupported constructs raise instead of vanish. Recommended path: land the decompiler + `simplify` work and the test harness first (they are independent and good), then do the converter as a sequence that converts from the AST.

## 3. Blocking issues

**B1. Silent wrong results for constructs the planner discards.** Each of these returns rows without error:
- `SELECT DISTINCT ON (a) a, b FROM t ORDER BY a, b` -> 5 rows instead of 4 (planner turns it into an Aggregate grouped on all projections).
- `SELECT a, ROW_NUMBER() OVER (ORDER BY a) AS rn FROM t QUALIFY rn = 1` -> 3 rows instead of 1.
- `... LIMIT 2 OFFSET 1` on the locked sqlglot (28.9) -> OFFSET dropped. The branch *xfails* this (`test_parse_sql.py:91-94`) instead of raising, and the gate `vparse(sqlglot.__version__) < vparse("30")` is wrong: on sqlglot 30.0–30.17 the test would fail outright and the result is still wrong.
- A user column aliased `_h` is dropped from the output (`sql.py:675` filters any projection named `_h`).
- `WHERE b = NULL` -> `b IS NULL` (main raised; branch returns the NULL rows). `TRY_CAST(b AS INTEGER)` -> `CAST` (`sge.TryCast` is a subclass of `sge.Cast`, caught by `sql.py:1209`), which raises at runtime on bad values and silently changes semantics on good ones.
Fix: the converter has the AST; read `select.args["offset"]`/`limit`/`distinct.on`/`qualify` from it (it already does exactly this for set operations at `sql.py:766-790`) and raise `com.UnsupportedOperationError` for anything it does not translate. The default `convert` must not be `raise TypeError(type(step))` (`sql.py:348`); see B5.

**B2. The rule-set choice regresses plain derived tables.** With `merge_subqueries` dropped, sqlglot's `Scan.from_expression` returns the *inner* step for a `FROM (SELECT ...) s` and `Step.from_expression` then overwrites its projections with the outer ones (`sqlglot/planner.py:223`, `step.projections = projections`), so the inner computed columns are gone. Reproduction on the branch: `SELECT s.z FROM (SELECT a + c AS z FROM t) s` -> `IbisTypeError: Column 'z' is not found in 's'`; same for `SELECT s.aa FROM (SELECT a AS aa FROM t) s WHERE s.aa > 1`. The planner output for the WHERE variant is literally `Scan s proj=['"s"."z" AS "z"'] cond="t"."a" + "t"."c" > 3` with no definition of `z`. The `candidates()` fallback at `sql.py:141-153` ("unknown aliases fall back to the relation being built") is what makes pass-through columns survive this by luck; it cannot work for computed or renamed columns. These worked on main (merge_subqueries inlined them). This is the planner relying on an optimizer rule the branch removed, i.e. exactly tobymao's "the planner is used to facilitate execution" (https://github.com/tobymao/sqlglot/pull/2503#issuecomment-1791119658). Re-enabling `merge_subqueries` fixes the class and costs TPC-DS q33/q54/q56/q58/q60/q83 (IntegrityError in the converter); that is a converter gap, not a reason to keep the lossy path. Either fix those six with `merge_subqueries` on, or (better) stop planning derived tables through `sqlglot.planner` at all.

**B3. The comparator is tuned to hide a real typing deviation and never checks order or names.** `assert_same_rows` (`test_parse_sql.py:64-88`) rounds every numeric column to two decimals and then applies `atol=0.011`; for TPC-DS ratio columns in the 0.01–1 range that is a 1–100 % tolerance. It is there because Ibis types `mean()` of `decimal(p, s)` as `decimal(p, s)` (`ibis/expr/operations/reductions.py:222-232`, `dt.higher_precedence(dtype, dt.float64)` picks the decimal) while DuckDB returns DOUBLE; `PandasData.convert_table` then rounds the result to `s` places. `SELECT AVG(CAST(c AS DECIMAL(10,2))) FROM t` returns 2.12 instead of 2.125. Twelve TPC-DS queries and TPC-H q01 differ for this reason. This is an Ibis typing bug (an AVG of a 2-scale decimal is not a 2-scale decimal in any engine I know), not something the parser should cast around, and it should be an issue/PR of its own; until then the tests should mark the affected queries or compare at a documented tolerance, not round everything. Separately: the comparator sorts rows, so `ORDER BY` is never verified (I passed a deliberately reversed sort through it), and `test_decompile_tpch.py:136,160` does `expected_df.columns = result_df.columns`, so output names are never verified either. Observed name deviations that no test can see: `SELECT a AS "MyCol"` -> `mycol`; unaliased expressions -> `_col_0` (DuckDB: `count_star()`); `SELECT * FROM t JOIN u` -> `a_1` where SQL keeps `a`. Also, `parse_sql(sql)` without `dialect` parses `ORDER BY a` as NULLS FIRST (sqlglot's generic null ordering) while DuckDB's default is NULLS LAST; `test_parse_sql_tpch` calls `parse_sql(sql, tpch_catalog)` with no dialect.

**B4. sqlglot coupling is broken at both ends of the declared range.** At import: `@convert.register(sge.SetOperation)` (`sql.py:684`) breaks `import ibis` on sqlglot < 26. At runtime: `select.args.get("with_")` (`sql.py:692`) is `None` on sqlglot < 28, so CTEs are silently not pre-bound (and the `.view()` logic for a CTE scanned twice does not apply). No CI job tests the lower bound, but cpcloud will ask. Either bump the floor to `>=28` with the bump justified in the commit, or absorb both names (`select.args.get("with_") or select.args.get("with")`, `getattr(sge, "SetOperation", sge.Union)`); do not add version branches. And fix the OFFSET xfail gate to `< 30.18` (or better, remove the dependency on the planner's offset entirely per B1).

**B5. Error messages for unsupported SQL are not acceptable for a public function.** Examples from the branch: `TypeError: <class 'sqlglot.expressions.MD5'>`, `KeyError: <class 'sqlglot.expressions.IntDiv'>`, `KeyError: 's'` (derived table with a window or LIMIT inside), `KeyError: ''` (VALUES, LATERAL), `KeyError: '_0'` (PIVOT), `AttributeError: 'Table' object has no attribute 'name'` (scalar subquery in a SELECT list), `IbisTypeError: Column 'a' is not found in 't'` for `GROUP BY ROLLUP (a)`. The nine TPC-DS xfails surface as `Column 'channel' is not found in 'x'`, `IntegrityError: Cannot add Field to projection`, and `KeyError: <class 'sqlglot.expressions.Grouping'>`, none of which says "ROLLUP is not supported". Replace the `singledispatch` default and the `_binary_operations[type(...)]`/`_reduction_methods[type(...)]` lookups with one `com.UnsupportedOperationError(f"... {node.sql()}")`, and detect ROLLUP/CUBE/GROUPING SETS/QUALIFY/DISTINCT ON/LATERAL/PIVOT up front.

**B6. The notes file and its two `chore(sql)` commits must not be in the PR**, and the architecture section of the notes should be corrected before it becomes a PR description: "dropping pushdown_projections broke q02" does not reproduce; "every silent-wrong case was a gap in the Ibis conversion code, not information lost by the planner" is contradicted by B1 and B2.

## 4. Non-blocking issues and suggestions

**Converter (`ibis/expr/sql.py`)**
- Everyday constructs that raise on the branch (all would be natural targets for the "everyday" suite): scalar subquery in a SELECT list (`SELECT a, (SELECT MAX(a) FROM u) FROM t`, correlated or not); `SUM(c) / COUNT(*)` (`convert_count` returns a Deferred `ibis._.count()` that cannot sit inside an expression, `sql.py:1187-1195`; #9267's exact case `COUNT(*) AS n` works); `RANK() OVER (ORDER BY SUM(c))` with GROUP BY; `SELECT a, COUNT(*) AS a ... GROUP BY a`; NATURAL JOIN; `IS [NOT] DISTINCT FROM` (also as a join key); ANY/ALL subqueries; `FILTER (WHERE ...)`; `SUM(DISTINCT x)`; BOOL_OR/BOOL_AND; STRING_AGG; `//`; DATE_DIFF/DATEDIFF; CURRENT_DATE; EXP/LOG; POSITION/STRPOS; SPLIT_PART; REGEXP_MATCHES; DATE_PART; `EXTRACT(dow ...)` (maps to a nonexistent `.dow()`; Ibis spells it `day_of_week`); `a + NULL`; WITH RECURSIVE; VALUES; UNNEST; LATERAL.
- `convert_substring` (`sql.py:1238`) subtracts 1 unconditionally; SQL `SUBSTRING(x, 0, n)` and negative starts are engine-defined and both come out wrong on DuckDB. Either translate exactly for the dialect or raise for non-positive starts.
- `convert_window` (`sql.py:1055-1075`): the default-frame rule (`range=(None, 0)` for ordered aggregate windows) is right for SQL; note that `MAX(c) OVER (ORDER BY a)` etc. pass my tests. Ranking `+1` (`sql.py:997-1004`) is right. `CONCAT` via `coalesce(arg, '')` is right for DuckDB/Postgres but not for MySQL/Oracle where CONCAT propagates NULL; it should be keyed on the dialect, which the function already has access to via `func.args.get("safe")` only partially.
- `Catalog` (`sql.py:43-231`) plus `_chain_column`/`_trace_name` (`sql.py:246-296`) is ~250 lines of name resolution with four heuristics layered on each other (step binding beats registry beats outer fallback; join-key counterpart lookup; rename tracing). Each one has a query that forced it, but none has a unit test of its own, and the `candidates()` outer fallback is what papers over B2. If the converter moves to the AST, most of this collapses: a derived table or CTE becomes a bound `ir.Table`, a join member is addressed by its alias, correlation is a scope stack. If it stays, each heuristic needs a focused test in `ibis/expr/tests/test_sql.py` that fails without it.
- `replace_operands` (`sql.py:580-634`) now also splits window items out of the Aggregate step; the `_w_N` naming is "ours" but lives next to the planner's `_a_N`, which a reader cannot tell apart. A comment-level fix at minimum.
- `_is_true` and the inline `pred.op() == ops.Literal(True, dt.boolean)` in `apply_condition` duplicate each other.
- `.view()` for every second scan of a base table (`sql.py:373`) is correct for self joins and correlated references but also fires for a table scanned in two unrelated CTEs; it is harmless semantically and only costs readability (`selfreference = supplier.view()` in decompiled q02).

**Decompiler (`ibis/expr/decompile.py`)**
- `exists_subquery` (`decompile.py:174-183`): `(pred).any()` is correct when the predicate spans exactly {inner, outer} and the Deferred is resolved by `.filter`/`.select` on that outer (`ibis/expr/types/logical.py:326-342` picks "the relation that is not `_`"). It raises `ValueError` if the outer in the predicate is not the table the filter is applied to (see the `simplify` bug below). The fallback `(rel.count() > 0)` is semantically equivalent to EXISTS in all NULL/empty cases (COUNT(*) is never NULL) and is fine; its only cost is readability. Nested EXISTS inside EXISTS counts relations as 1 (Subquery.relations is empty) and takes the fallback, which is also fine.
- Binding every `JoinReference` parent to a variable (`decompile.py:613-622`) is the right fix: a join member is referenced from predicates and the chain's select, so it must have a name. Good.
- Parse OK but decompile breaks: `PERCENT_RANK()`/`CUME_DIST()` -> `ValueError: not enough values to unpack` at `decompile.py:134` (`this, *args = args` with no args); `DateSub`, `DateDiff`, `IntervalMultiply` -> `KeyError` (no method mapping); `NULLIF` -> `.null_if()` from the snake-case fallback (`nullif` is the method). This is the whack-a-mole cpcloud warned about in https://github.com/ibis-project/ibis/pull/4535#discussion_r975438597 and the reason #11810 exists; worth a line in the PR acknowledging that `_method_overrides` keeps growing.
- Readability vs the hand-written TPC-H queries in `ibis/backends/tests/tpc/h/test_queries.py`: q04, q13, q17, q21 are close to what a person would write (q04/q21 use `.any()` exactly like the hand-written version). q02 is not: three `.view()`s, variables `p..p6`, `p3.cross_join(supplier).inner_join(p, [two keys])` (the planner's join shape), a redundant re-filter of `region`, and every scan carrying a `.select(...)` from `pushdown_projections`. Since the suites pass without `pushdown_projections`, dropping it removes the `.select()` noise and the "decompiler bug" the notes blame it on. `ibis.literal("%BRASS")` and `ibis.literal(...)` for every `isin` member are the `literal` rule choosing the typed form; a maintainer will ask for plain Python literals where the inferred type matches.
- `aggregation` now supports `by=` only; `dummy_table` renders `lit.as_table().mutate(...)` for FROM-less selects. Fine.

**`simplify` (`ibis/expr/rewrites.py`)**
- The window guard in `reorder_filter_project` (`rewrites.py:396`) is correct and minimal: pushing any filter below a projection that computes a window changes the window's input, regardless of what the filter references (I confirmed the guard also holds for a filter that does not touch the window column). This is a correctness bug in `simplify` independent of this branch and should be its own small `fix` PR with `test_simplify_keeps_window_above_filter`.
- The same rule has a second, pre-existing hole the branch did not close: a filter whose predicate contains a correlated subquery referencing the projection. Repro: `p = t.select(t.a, c=t.a + 1); p.filter((u.a == p.c).any())` -> `simplify` produces a tree that compiles to `Binder Error: Referenced table "t2" not found`, and `decompile`+`exec` raises `ValueError: too many values to unpack`. Cause: `v.replace(rule, filter=ops.Value)` does not descend into `Subquery.rel`, so the subquery keeps pointing at the projection that was just moved above the filter. The guard should be "no window in the projection and no `ops.Subquery` in the predicates", not window-only.
- The `keep` context for `complete_reprojection` (`rewrites.py:366-369, 415-416`) works and has precedent (`context=` is used at `rewrites.py:282,356`), but it is a workaround for `ops.InSubquery.__init__` (`subqueries.py:73-82`) doing `(value,) = rel.values.values()`, which rejects a bare table, while `ScalarSubquery.value` (`subqueries.py:49-57`) already falls back to `rel.fields`. Mirroring that fallback in `InSubquery` removes the need for `keep` entirely and is the fix kszucs would make.

**Tests / CI**
- Location: executing tests under `ibis/backends/duckdb/tests` is consistent with how #9779 did it and with the marker/data wiring; fine. `test_decompile_tpch.py` importing `assert_same_rows`/`roundtrip` from `test_parse_sql.py` should move those helpers to a conftest or `ibis/backends/tests/tpc/conftest.py`.
- The `parse`/`roundtrip` parametrisation is good. The 9 ROLLUP xfails should be `xfail(strict=True)` with the reason naming the construct, and the OFFSET xfail should become an expected `UnsupportedOperationError` per B1.
- Snapshot churn in `ibis/expr/tests/snapshots/test_sql/**`: the diffs are improvements (`ibis.literal(True)` join predicates gone, `SELECT COUNT(first_name)` now correctly `first_name.count()` instead of `count()`, scalar subquery as `.as_scalar()` instead of a cross join). The per-scan `p = employee.select(employee.id)` lines are the `pushdown_projections` artifact and would disappear with it.
- `ibis/backends/duckdb/tests/test_decompile_tpch.py::test_parse_sql_tpch` still passes no dialect; pass `"duckdb"` for consistency with the result tests.

**Commits / PR hygiene**
- Scope: `sql` is already used in this repo for the SQL *compiler* (`refactor(sql): make compilers usable with a base install`, `fix(sql): outer order by ...`), so `feat(sql)` for the parser is ambiguous. Precedent for this file is `feat(ir)` (#4853), `fix(ir)` (#7538), `fix(parse_sql)` (#7617); use `parse_sql`. `fix(decompile)` for the `rewrites.py` change is defensible since `simplify` is only called from `decompile.py:605`, but the window bug is a `simplify` bug whoever calls it; `fix(ir)` or `fix(rewrites)` with "decompile" in the body is more honest. Headers are all exactly 50 chars; commitlint allows 120, so there is room for a clearer subject than "simplify leaves windows unfiltered" (which reads as a statement of the bug, not the fix).
- Two open PRs will conflict: cpcloud's #9945 (rollup/cube/grouping sets) changes the decompiler's `Aggregate` rule signature and raises `NotImplementedError` for grouping sets, which is also the right home for the ROLLUP story here; NickCrews's #11100 touches `to_sql` in `ibis/expr/sql.py`. Rebase order needs a sentence in the PR.
- No public API changes; `parse_sql` and `decompile` stay `@experimental`, which matches the maintainers' stance (kszucs asked for experimental in #4535, cpcloud asked "do we have this marked experimental" in #9779, `docs/_quarto.yml:355` still says "add decompile here once the API is not experimental"). Do not propose docs in these PRs.

## 5. Where this sits against the maintainers' stated plans

- The tracking issue #9529 has no maintainer design commitment; gforsyth's plan was "see what it takes to take TPC-H query 1 from SQL -> Ibis Python and then use that as a guide" (https://github.com/ibis-project/ibis/issues/9529#issuecomment-2233866255). jcrist re-opened #9979 "since this is well scoped to handling only TPC-H queries, and is just focused on the parse_sql functionality (not the rest of the decompiler)" (https://github.com/ibis-project/ibis/issues/9979#issuecomment-2345077173). The branch meets that bar for the expression side and goes past it to TPC-DS; the execute-and-compare gate is exactly the method gforsyth used in #9779 ("re-using the values comparison from the regular TPCH tests ... executing that against TPCH data and comparing it to running the sql query against DuckDB", https://github.com/ibis-project/ibis/pull/9779#issuecomment-2276009398). Decoupling parse_sql correctness from decompile snapshots also fixes the coupling contributors complained about in #7610/#7617.
- On the planner: the original prototype PR #4853 was merged with zero review of the design ("Note, that this is far from being complete and bug free", kszucs; "let's merge it so we can iterate", https://github.com/ibis-project/ibis/pull/4853#issuecomment-1359321063). gforsyth's #9779 description is the most explicit maintainer statement: the planner "replaces a few items with aliases. In other places, it doesn't use fully-qualified column names. Both of these prevent us from reliably converting into an Ibis expression", and the sort-key handling was "definitely the most brittle part" (https://github.com/ibis-project/ibis/pull/9779). cpcloud's answer to #9254 ("use sqlglot's AST") was "we are already leveraging SQLGlot's AST ... The remaining and quite large effort is to add test cases, features, and fix bugs" (https://github.com/ibis-project/ibis/issues/9254#issuecomment-2135291435): no attachment to the planner, and his #9510 comment identifies column qualification as the core problem, which the optimizer's `qualify` rules solve without the planner. tobymao: "it's not the goal of the planner, the planner is used to facilitate execution" (reverting a fidelity fix as "not necessary", https://github.com/tobymao/sqlglot/pull/2503#issuecomment-1791119658), "No plans to do this" for Step -> expression (https://github.com/tobymao/sqlglot/issues/1594#issuecomment-1544191421); the executor it serves is documented as "still in an experimental stage" and built "just for entertainment", while the README positions the optimizer's canonical AST as "the foundations for implementing an actual engine". The branch's evidence (B1, B2, OFFSET only arriving in 30.18, set-operation sides lost, set-valued dependencies) is consistent with all of that.
- cpcloud's review concerns on record: COUNT(*) vs COUNT(col) null semantics (https://github.com/ibis-project/ibis/pull/9779#discussion_r1707007257, the branch gets this right), generic `Value` rendering over per-op overrides (#4535), snapshot files as generated (#7538), experimental status.
- jcrist on what decompile output is for: "a starting point that a human can then edit further ... I don't expect the generated code to match 1:1 with how a human would write it" (https://github.com/ibis-project/ibis/issues/4335). The q02 output is a starting point; q04/q21 are nearly finished code.
